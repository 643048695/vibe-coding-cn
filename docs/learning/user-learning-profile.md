# 个性化学习画像与进度

> 用途：这是本仓库的个性化教学入口。开始教学前先读本文件，再结合当前仓库真实内容选课与讲解。
> 原则：以用户真实反馈为最高优先级；本文件用于减少上下文丢失，不替代仓库原始文档。

## 1. 学习目标

- 目标方向：AI 落地工程师 / FDE / Agent 工程实践。
- 当前特点：不会传统代码开发，但长期使用 Codex / Agent 做真实项目。
- 学习重点：不是背语法，而是建立工程判断力，能够看懂系统行为、判断 Agent 方案、发现过度设计、识别错误边界与验证结果。
- 目标能力：
  - 能与 Agent 高质量沟通。
  - 能判断一个设计是否合理，而不是只听 Agent 自报。
  - 能理解执行链、数据流、状态、依赖、边界、错误与验证。
  - 能把抽象工程概念用于真实项目。

## 2. 教学偏好

### 强偏好

- 少讲抽象定义，多讲“这个东西我马上能拿来做什么”。
- 优先用真实开发场景，再解释概念名称。
- 最好使用用户熟悉的《环世界》做类比，但类比必须服务于实际工程判断，不能只增加趣味。
- 每一课都应尽量给一个可以直接拿去问 Agent 的短句。
- 用户不会代码，所以重点讲：
  - 系统实际怎么运行。
  - 谁先谁后。
  - 谁读取谁。
  - 谁修改谁。
  - 什么是事实。
  - 什么是派生。
  - 失败后发生什么。
  - Agent 的修改会影响什么。
- 对简单概念快速讲完，不要为了完整而过度展开。
- 对高价值概念可以深入，但要持续说明“实际用途”。

### 不喜欢

- 重复讲“目标、计划、验证”之类已经理解的基础理念。
- 纯概念罗列。
- 长篇哲学解释但没有真实用途。
- 反复讲多 Agent 分工、总控调度等用户已经实际在使用的内容。
- 让用户充当人工中转站，不断复制 Agent 之间的信息。
- 只告诉用户代码文件名、类名、函数名，而不解释行为变化。
- Agent 式理想化案例：现实项目中 Agent 会不断加 adapter、fixture、fallback、schema、脚本，导致越修越复杂，因此教学必须考虑真实工程复杂性。

## 3. 推荐教学格式

每个知识点优先采用：

1. 一个真实问题。
2. 一个用户熟悉的例子。
3. 解释背后的工程概念。
4. 说明这个概念在真实 Agent 项目中会怎么出错。
5. 告诉用户如何判断。
6. 最后只给 1 句简短的 Agent 沟通句。

示例：

> 别跟我解释代码，告诉我这个改动的执行行为：什么触发 → 按什么顺序执行 → 谁等谁 → 改了什么状态 → 失败会怎样 → 会不会重复/并发。最好给改动前后对比。

## 4. 用户熟悉的类比体系

用户平常较多玩《环世界》（RimWorld）。

可使用但不要滥用：

- 殖民者能力 → 模型能力。
- 工作优先级 → Agent 调度优先级。
- Allowed Area → 权限 / 修改范围。
- Bill → Spec / 验收目标。
- Alert → Eval / Quality Gate。
- 资源争抢 → 并发竞争 / 共享资源。
- 科技树前置 → 任务依赖。
- 不同殖民者分工 → 多 Agent 角色分工。

注意：用户已经熟悉“总控 Agent 只负责调度子 Agent”的模式，因此不要继续把多 Agent 调度作为主要教学内容，除非出现更深的新问题。

## 5. 当前已学习内容

### 已建立基础认知

- 问题求解：现状、目标、差距、标准。
- 拼好码 / Glue Coding：成熟能力优先，胶水连接，不轻易重复造轮子。
- 递归自优化系统：不要只修单次输出，要关注生成机制与长期反馈。
- Harness Engineering：
  - 模型不是可靠性来源。
  - 外部验证、约束、反馈、证据比模型自评更重要。
  - 诊断与修复应分离。
  - 修复需要限制修改半径。
- 思维模型：
  - 现象学还原：先看事实。
  - 贝叶斯更新：保留多个候选原因，用证据更新。
  - 可证伪性：寻找能推翻假设的证据。
  - 奥卡姆剃刀：定位原因后优先最小修复。

### 组合描述模型已学习

- 对象 vs 状态。
- 快照 vs 状态。
- 变换链：找“第一次从正确变成错误”的位置。
- 关系错误：
  - 语义不一致。
  - 单位不一致。
  - 责任不一致。
  - 时序不一致。
  - 失败语义不一致。
- 事实所有权：同一事实应该有明确最终 owner。
- 核心数据 vs 派生数据：能从核心事实稳定计算出来的东西，不要轻易维护第二份真相。

### 语言层已学习到

- L4 执行模型：
  - 重点不是看懂 await 等语法。
  - 重点是知道“什么时候执行、谁等谁、谁先谁后”。
- L9 时间维度思想：
  - 是否重复、延迟、并发执行。
- L2 数据模型开始学习：
  - 复制 vs 共享。
  - 修改 A 时 B 跟着变化，可能是共享引用。
  - 外层复制不代表内部没有共享（浅拷贝问题）。

### 当前可直接用于审 Agent 的短句

1. 执行模型：
   > 别讲代码，给我讲执行链和改动前后行为。

2. 更完整执行审查：
   > 什么触发 → 按什么顺序执行 → 谁等谁 → 改了什么状态 → 失败会怎样 → 会不会重复/并发？

3. 数据共享：
   > 这里是复制还是共享？改它会影响谁？

4. 变换链：
   > 原始意图经过了哪些表示？第一次在哪一步变错？

5. 事实所有权：
   > 这个事实到底谁有最终决定权？其他地方只是读，还是也能改？

6. 派生数据：
   > 这个值能不能从现有事实重新算？如果能，为什么要再存一份？

当前已完成：

- L2 中“复制 vs 共享”的第一部分。

推荐下一课：

> 错误处理与边界：为什么 Agent 加 try/catch、fallback、默认值后“系统不报错了”，但真实错误反而被藏起来。

重点不要教具体语法，重点讲：

- 错误是向上传递、被吞掉，还是被转换。
- fallback 什么时候是容错，什么时候是在伪造成功。
- 默认值如何掩盖缺失事实。
- 为什么“没报错”不等于“正确”。
- 用户如何要求 Agent 展示失败路径。

## 7. 教学动态调整规则

每次教学后根据用户反馈更新本文件：

- 用户说“有用”：提高同类内容优先级。
- 用户说“无聊/用不到”：降低该类内容优先级，不重复。
- 用户要求“简短”：将可记忆内容压缩为一句 Agent 沟通语。
- 用户表现出已经实际掌握某实践：跳过基础概念，进入更深层问题。
- 新学到的重要能力，应追加到“当前已学习内容”和“可直接用于审 Agent 的短句”。
- 每隔若干课重新检查学习路线，不机械按文档顺序推进。

## 8. 教学时的仓库使用原则

- 优先使用本仓真实文件，不凭空生成课程。
- 允许跨 docs / research / skills 组合内容，只要能提升实际价值。
- 不要求按仓库目录顺序教学。
- 优先挑对用户真实 Agent 开发有直接帮助的内容。
- 解释时区分：
  - 仓库原始观点。
  - 基于仓库观点做的教学类比。
  - 针对用户实际场景给出的应用建议。
